# `dispatchReplyFromConfig` 函数技术文档

## 函数签名

```typescript
export async function dispatchReplyFromConfig(
  params: DispatchFromConfigParams,
): Promise<DispatchFromConfigResult>;
```

## 位置

- **文件**: `src/auto-reply/reply/dispatch-from-config.ts`
- **起始行**: 334
- **结束行**: 1549

---

## 一句话理解

> **这是消息分发的"总指挥部"——负责决策、协调、监控，最终调用 Agent 执行。**

---

## 输入输出

### 输入：我要处理什么？

| 参数           | 是什么     | 通俗理解                   |
| -------------- | ---------- | -------------------------- |
| `ctx`          | 消息上下文 | "谁在哪个渠道发了什么消息" |
| `cfg`          | 配置对象   | "系统怎么配置的"           |
| `dispatcher`   | 分发器     | "怎么把回复发出去"         |
| `replyOptions` | 执行选项   | "回调函数、中断信号等"     |

### 输出：处理结果是什么？

| 结果          | 含义                                 |
| ------------- | ------------------------------------ |
| `queuedFinal` | 是否已排队发送最终回复               |
| `counts`      | 发送了多少条消息（final/block/tool） |

## 详细处理步骤

### Phase 1: 诊断与追踪初始化

**目的**: 给这次消息处理安装"黑匣子记录器"。

#### 提取的信息

```
┌─────────────────────────────────────────┐
│           从消息上下文提取               │
├─────────────────────────────────────────┤
│  channel     → 渠道标识（如 feishu）     │
│  chatId      → 聊天 ID（群组/私聊）      │
│  messageId   → 消息唯一 ID               │
│  sessionKey  → 会话键                    │
│  startTime   → 开始时间戳                │
└─────────────────────────────────────────┘
```

#### 创建的追踪函数（3 个"状态记录笔"）

| 函数                | 作用           | 触发时机     |
| ------------------- | -------------- | ------------ |
| `recordProcessed()` | 记录"处理完成" | 函数结束时   |
| `markProcessing()`  | 记录"正在处理" | Agent 执行前 |
| `markIdle()`        | 记录"空闲状态" | 处理完成后   |

**一句话总结**: 这一步只是"准备记录工具"，真正的记录发生在后续各个退出点。

### Phase 2: 入站去重检查

**目的**: 防止同一条消息被重复处理。

#### 工作原理

```
消息到达
    │
    ▼
┌─────────────────────┐
│  claimInboundDedupe │  ← 在内存中"认领"这条消息
└──────────┬──────────┘
           │
           ▼
     ┌─────────────────────────────────────┐
     │         检查认领结果                 │
     ├─────────────────────────────────────┤
     │                                     │
     │  ┌─────────┐     ┌─────────────┐   │
     │  │duplicate│     │  inflight   │   │
     │  │已处理过 │     │ 正在处理中  │   │
     │  └────┬────┘     └──────┬──────┘   │
     │       │                │           │
     │       └────────────────┘           │
     │                │                   │
     │                ▼                   │
     │         [直接跳过返回]              │  ← 退出点 1
     │                                     │
     │  ┌─────────┐                       │
     │  │ claimed │                       │
     │  │成功认领 │                       │
     │  └────┬────┘                       │
     │       │                            │
     │       ▼                            │
     │  [继续处理]                         │
     │                                     │
     └─────────────────────────────────────┘
```

**通俗理解**: 就像"领票排队"——如果票已经被领了（duplicate/inflight），你就不用再排队了。

#### 查询顺序（优先级从高到低）

```

│                                          │

│     (会话被绑定到特定目标)                │
│                                          │
│  2. 存储中的会话键                        │
│     (session-store.json 里的记录)        │
│                                          │
│  3. 请求中的会话键  ← 兜底                │
│     (消息本身携带的 SessionKey)           │
│                                          │
└──────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────┐
│          解析 Agent 信息                  │
├──────────────────────────────────────────┤
│  sessionAgentId  → 哪个 Agent            │
│  sessionAgentCfg → Agent 怎么配置        │
│  workspaceDir    → 工作目录在哪          │
└──────────────────────────────────────────┘
         │
         ▼
┌──────────────────────────────────────────┐
│          加载 Runtime Plugins            │
└──────────────────────────────────────────┘
```

**通俗理解**: 就像"查档案"——搞清楚这个会话属于谁、状态是什么、配置是什么。

### Phase 4: 跨渠道路由决策

**目的**: 判断回复应该发到哪个渠道。

#### 场景说明

```
┌─────────────────────────────────────────────────────┐
│                    路由场景                          │
├─────────────────────────────────────────────────────┤
│                                                     │
│  场景 A: 同渠道处理                                 │
│  ┌───────────────────────────────────────────┐     │
│  │  消息来自飞书 → session 在飞书              │     │
│  │  → 回复直接用 dispatcher 发到飞书           │     │
│  └───────────────────────────────────────────┘     │
│                                                     │
│  场景 B: 跨渠道路由                                 │
│  ┌───────────────────────────────────────────┐     │
│  │  消息来自 Telegram                         │     │
│  │  → 但 session 当前绑定在 Slack             │     │
│  │  → 回复需要路由回 Telegram（原渠道）        │     │
│  └───────────────────────────────────────────┘     │
│                                                     │
└─────────────────────────────────────────────────────┘
```

#### 决策输出

| 决策结果                   | 含义                   |
| -------------------------- | ---------------------- |
| `shouldRouteToOriginating` | 是否路由回原渠道       |
| `deliveryChannel`          | 实际发送渠道           |
| `shouldSuppressTyping`     | 是否抑制"正在输入"提示 |

### Phase 5: Plugin 绑定处理

**目的**: 如果会话被绑定到特定 Plugin，让 Plugin 优先处理。

#### 处理流程

```
┌─────────────────────────────────────────┐
│    检查：会话是否绑定到 Plugin?          │
└─────────────────┬───────────────────────┘
                  │
        ┌─────────┴─────────┐
        │                   │
      Yes                  No
        │                   │
        ▼                   ▼
┌─────────────────┐   [继续正常流程]
│ 调用 Plugin     │
│ inbound_claim   │
│ handler         │
└────────┬────────┘
         │
         ▼
┌─────────────────────────────────────────────────┐
│              Plugin 处理结果                     │
├─────────────────────────────────────────────────┤
│                                                 │
│  ┌──────────┐                                  │
│  │ handled  │  → Plugin 已处理完               │
│  │          │  → 直接返回 [退出点 2]            │
│  └──────────┘                                  │
│                                                 │
│  ┌──────────┐                                  │
│  │ declined │  → Plugin 拒绝处理               │
│  │          │  → 发拒绝提示，返回 [退出点 3]    │
│  └──────────┘                                  │
│                                                 │
│  ┌──────────┐                                  │
│  │  error   │  → Plugin 处理出错               │

│                                                 │
│  ┌──────────────────┐                          │
│  │ no_handler /     │                          │
│  │ missing_plugin   │  → Plugin 没有处理器     │
│  │                  │  → 回退到 Agent 处理     │
│  └──────────────────┘                          │
│                                                 │
└─────────────────────────────────────────────────┘
```

**通俗理解**: 就像"VIP 通道"——如果会话有专属 Plugin，先让 Plugin 处理；Plugin 搞不定才走普通流程。

```
                  │
        ┌─────────┴─────────┐
        │                   │
      Yes                  No
        │                   │
        ▼                   ▼
┌─────────────────┐   [跳过，继续]

└────────┬────────┘
         │
         ▼
┌─────────────────────────────────────┐
│         Plugin 返回结果              │
├─────────────────────────────────────┤
│                                     │
│  ┌──────────┐                      │
│  │ handled  │  → Plugin 拦截了     │
│  │          │  → 用 Plugin 的回复  │

│                                     │
│  ┌──────────┐                      │

└─────────────────────────────────────┘
```

**通俗理解**: 就像"安检门"——Agent 执行前，Plugin 可以检查并决定是否放行。

```

│                     策略库                          │
├─────────────────────────────────────────────────────┤
│                                                     │
│  ┌─────────────────────────────────────────────┐   │
│  │              发送策略                        │   │
│  │  resolveSendPolicy                           │   │
│  ├─────────────────────────────────────────────┤   │
│  │  输出:                                       │   │
│  │  • suppressDelivery → 是否抑制自动发送       │   │
│  │  • 用途: 控制 Agent 是否自动回复             │   │
│  └─────────────────────────────────────────────┘   │
│                                                     │
│  ┌─────────────────────────────────────────────┐   │
│  │              工具策略                        │   │
│  │  resolveEffectiveToolPolicy                  │   │
│  ├─────────────────────────────────────────────┤   │
│  │  输出:                                       │   │
│  │  • globalPolicy    → 全局工具权限            │   │

│  │  • profile         → 用户 Profile 权限       │   │

│  └─────────────────────────────────────────────┘   │
│                                                     │
│  ┌─────────────────────────────────────────────┐   │
│  │              源回复策略                      │   │

│  │  • suppressTyping → 是否抑制输入提示         │   │
│  │  • 用途: 控制回复怎么显示、发不发 typing     │   │
│  └─────────────────────────────────────────────┘   │
│                                                     │
└─────────────────────────────────────────────────────┘
```

**通俗理解**: 就像"规则手册"——告诉 Agent 能做什么、不能做什么、怎么做。

### Phase 11: Agent 执行调用

**目的**: 真正调用 Agent（模型）处理消息。

#### 调用结构

```
┌─────────────────────────────────────────────────────┐
│              getReplyFromConfig                     │
│                 (Agent 执行器)                       │
├─────────────────────────────────────────────────────┤
│                                                     │
│  输入:                                              │
│  ├─ ctx        → 消息内容                          │
│  ├─ cfg        → 配置                              │
│  └─ replyOptions → 各种回调                        │
│                                                     │
│  回调函数（由 dispatchReplyFromConfig 注入）:       │
│  ├─ onToolResult  → 工具执行结果怎么发             │
│  ├─ onPlanUpdate  → 计划更新怎么发                 │
│  ├─ onBlockReply  → 流式块怎么发                   │
│  ├─ onApprovalEvent → 审批事件怎么发               │
│  └─ onPatchSummary → Patch 总结怎么发              │
│                                                     │
│  输出:                                              │
│  └─ replyResult → Agent 生成的回复                 │
│                                                     │
└─────────────────────────────────────────────────────┘
```

#### 回调的作用

```
┌─────────────────────────────────────────────────────┐
│     为什么用回调而不是直接调用 dispatcher?          │
├─────────────────────────────────────────────────────┤
│                                                     │
│  Agent 执行层不需要知道:                            │
│  ├─ 回复发到哪个渠道                                │
│  ├─ 是否要加 TTS                                    │
│  ├─ 媒体路径怎么规范化                              │
│  └─ 是否要路由到原渠道                              │
│                                                     │
│  这些都由 dispatchReplyFromConfig 在回调里处理:     │
│                                                     │
│  onToolResult(payload) {                            │
│    ├─ 加 TTS                                        │
│    ├─ 规范化媒体路径                                │
│    ├─ 判断路由还是 dispatcher                       │
│    └─ 发送                                          │
│  }                                                  │
│                                                     │
└─────────────────────────────────────────────────────┘
```

**通俗理解**: 就像"指挥官下达命令，士兵执行，指挥官控制怎么汇报"。

### Phase 12: 最终回复发送与 TTS 补充

**目的**: 把 Agent 生成的回复发送出去。

#### 发送流程

```
┌─────────────────────────────────────────────────────┐
│              处理 Agent 返回的回复                   │
├─────────────────────────────────────────────────────┤
│                                                     │
│  replyResult (可能是数组)                           │
│      │                                              │
│      ▼                                              │
│  ┌─────────────────────────────────────────────┐   │
│  │  for each reply:                             │   │
│  │                                              │   │
│  │    ├─ 跳过 reasoning 类型（不显示思考过程）  │   │
│  │    │                                         │   │
│  │    ├─ maybeApplyTtsToReplyPayload            │   │
│  │    │  → 如果需要语音，生成 TTS               │   │
│  │    │                                         │   │
│  │    ├─ normalizeReplyMediaPayload             │   │
│  │    │  → 规范化媒体路径                       │   │
│  │    │                                         │   │
│  │    └─ 发送                                    │   │
│  │       ├─ shouldRouteToOriginating?           │   │
│  │       │  → routeReplyToOriginating           │   │
│  │       │  → 路由到原渠道                      │   │
│  │       │                                       │   │
│  │       └─ 否则                                  │   │
│  │          → dispatcher.sendFinalReply         │   │
│  │          → 用 dispatcher 发送                │   │
│  │                                              │   │
│  └─────────────────────────────────────────────┘   │
│                                                     │
└─────────────────────────────────────────────────────┘
```

#### TTS 补充（特殊场景）

```
┌─────────────────────────────────────────────────────┐
│           Block 流式完成后的 TTS 补充               │
├─────────────────────────────────────────────────────┤
│                                                     │
│  场景:                                              │
│  ├─ Block 流式发送完成                              │
│  ├─ 但没有生成最终回复（block 就够了）              │

│                                                     │
│  处理:                                              │

│  └─ 发送 TTS-only payload（只有音频，无文本）       │
│                                                     │
└─────────────────────────────────────────────────────┘
```

### Phase 13: 清理与返回

**目的**: 收尾——提交去重、标记状态、返回结果。

#### 清理流程

```
┌─────────────────────────────────────────────────────┐
│                    清理流程                         │
├─────────────────────────────────────────────────────┤
│                                                     │
│  1. 统计发送数量                                    │
│     counts = dispatcher.getQueuedCounts()           │
│     counts.final += routedFinalCount                │
│                                                     │
│  2. 提交去重                                        │
│     commitInboundDedupeIfClaimed()                  │
│     → 防止后续重复处理这条消息                      │
│                                                     │
│  3. 记录处理完成                                    │
│     recordProcessed("completed", ...)               │
│                                                     │
│  4. 标记会话空闲                                    │
│     markIdle("message_completed")                   │
│                                                     │
│  5. 返回结果                                        │
│     return { queuedFinal, counts }                  │
│                                                     │
└─────────────────────────────────────────────────────┘
```

#### 错误处理

```
┌─────────────────────────────────────────────────────┐
│                    错误处理                         │
├─────────────────────────────────────────────────────┤
│                                                     │
│  catch (err) {                                      │
│                                                     │
│    关键判断: inboundDedupeReplayUnsafe              │
│    ├─ true  → 已发送内容 → commitInboundDedupe     │
│    │              （不能重试，已发出去了）          │
│    │                                               │
│    └─ false → 未发送内容 → releaseInboundDedupe    │
│               （可以重试）                          │
│                                                     │
│    recordProcessed("error", ...)                    │
│    markIdle("message_error")                        │
│    throw err                                        │
│  }                                                  │
│                                                     │
└─────────────────────────────────────────────────────┘
```

## 设计要点

### 1. 分层架构

```
协调层（本函数）: 决策 + 协调 + 监控
    │
    ▼
执行层（getReplyFromConfig）: Agent 调用
    │
    ▼
发送层（dispatcher/路由）: 渠道 API 调用
```

### 2. 回调注入模式

Agent 不关心发送细节，通过回调让协调层控制：

- 发到哪个渠道
- 是否加 TTS
- 媒体路径怎么处理

### 3. 策略集中解析

所有策略在 Phase 10 统一解析，后续直接引用：

- 避免分散判断
- 便于调试和修改

### 4. 多重退出点

每个退出点都有完整清理：

- 记录处理结果
- 提交/释放去重
- 标记会话状态
